# eSIM как источник данных для Birge — Single Source of Truth

> Этот файл — единственный канонический документ о том, что такое eSIM-слой Birge,
> какие данные реально можно получать, как они питают рекомендации и анти-фрод,
> и что мы говорим жюри. Всё остальное (слайды, ответы, код) сверяется с ним.

---

## 1. TL;DR

eSIM сам по себе — это **не источник данных, а якорь идентичности**: криптографически
защищённый чип (eUICC) с уникальным EID, привязанный к физическому устройству.
Данные приходят **не с чипа, а от оператора** — через стандартизированные сетевые API
(GSMA Open Gateway / CAMARA: 33 выпущенных API, 140 коммерческих запусков на 85 сетях в 50 странах).
Для Birge это даёт два слоя ценности:
1. **Анти-фрод** (наш ключевой тезис): 1 устройство = 1 реальный участник группы.
2. **Сигналы для рекомендаций**: подтверждённая демография, регион, ценовой сегмент
   устройства, trust-скор — всё по согласию пользователя, server-side через оператора.

## 2. Техническая база (минимум, который нужно знать)

| Термин | Что это | Зачем нам |
|---|---|---|
| **eUICC** | Перепрошиваемый SIM-чип, впаянный в устройство | Физический якорь: не вынимается и не переставляется как пластиковая SIM |
| **EID** | Уникальный ID самого чипа (32 цифры, выдаётся на заводе) | «Паспорт устройства»: один EID = одно физическое устройство, навсегда |
| **ICCID** | ID конкретного профиля оператора на чипе | Меняется при смене оператора; EID — нет |
| **IMSI / MSISDN** | ID абонента в сети / номер телефона | Связка «человек ↔ оператор» |
| **RSP (GSMA SGP.21/22)** | Стандарт удалённой загрузки eSIM-профилей (SM-DP+) | Профили подписаны GSMA-сертификатами — подделать eSIM нельзя |

**Критичный технический факт (вопрос жюри №1):** мобильное приложение **не может читать
EID/IMSI напрямую** — iOS не даёт доступа вообще, Android требует carrier privileges.
Поэтому архитектура всегда такая: приложение → запрос к API оператора → оператор сверяет
по своей стороне (по IP-сессии абонента в его сети) → отдаёт результат «да/нет» или атрибут.
**Данные идут server-side от оператора, а не с чипа на клиенте.** Именно поэтому проект
имеет смысл как партнёрство с оператором — в этом и есть ответ «зачем здесь телеком».

## 3. Какие данные реально доступны (GSMA Open Gateway / CAMARA)

CAMARA — open-source стандарт API, под которым подписаны 86 операторских групп
(300+ сетей, 80% мировых подключений). Релевантные нам API:

### 3.1 Идентификация и анти-фрод
| API | Что возвращает | Используем для |
|---|---|---|
| **Number Verification** | Подтверждение «этот запрос идёт с устройства, владеющего номером X» — silent network auth, без SMS | Вход без SMS-кодов (наш onboarding-экран — это его UI-концепт) |
| **SIM Swap** | Дата/факт недавней перестановки SIM | Блок «угнанных» аккаунтов перед списанием холда |
| **KYC Tenure** | Как давно абонент у оператора | Trust-скор участника группы: 5 лет стажа ≠ вчерашняя симка |
| **Device Swap** | Менялось ли устройство под номером | Анти-мультиаккаунт: десять «новых устройств» за день = бот-ферма |
| **Verified Caller / Scam Signal** | Сигналы мошенничества | Защита P2P-приглашений в группы |

### 3.2 Сигналы для персонализации (всё — только с явного согласия)
| API / источник | Что даёт | Как питает рекомендации Birge |
|---|---|---|
| **KYC Match / Age Verification** | Подтверждённые имя, возраст (сверка с данными договора) | Точная демография вместо самодекларации: возрастные категории товаров, 18+ фильтры |
| **Device Location Verification** | «Устройство в зоне X?» (грубая, по соте) | Городские группы: консолидация доставки, «популярно в Алматы» становится фактом, а не предположением |
| **Device Roaming Status** | Абонент в роуминге / вернулся | Триггер «travel»-подборок (адаптеры, чемоданы) и пауза доставок |
| **Mobile Device Identifier** | Модель устройства (TAC) | Ценовой сегмент: iPhone 17 Pro и бюджетный Android → разные дефолтные бюджеты ленты (наш слайдер бюджета калибруется сам) |
| **Customer Insights** (в разработке CAMARA) | Агрегированные поведенческие сигналы оператора | Будущее: сегменты «студент/семья/бизнес» для cold-start |
| **Population Density Data** | Агрегаты плотности по зонам | Прогноз сбора групп по районам (наш predictFill v2) |
| **Carrier Billing** | Оплата со счёта телефона | Холд без банковской карты — снимает главный барьер первой покупки |

### 3.3 Чего НЕТ и не будет (говорим честно, если спросят)
- Содержимое звонков/SMS, история браузера — недоступны и не нужны.
- Точная GPS-геолокация — нет; только грубая (сота) и только verify-режим («в зоне X? да/нет»).
- Прямое чтение данных с чипа приложением — невозможно (см. §2).

## 4. Маппинг на нашу модель рекомендаций

Сейчас скоринг ленты: `интересы(+3) + бюджет(+2) + город(+1.5) + почти-собрана(+2) + рейтинг(+0.5)`.
Каждый сигнал самодекларирован в онбординге. eSIM-слой заменяет декларации фактами:

| Фича скоринга | Сейчас (MVP) | С eSIM-слоем |
|---|---|---|
| Город | Пользователь выбрал чипом | Location Verification: фактический домашний регион → группы своего города, реальная консолидация карго |
| Бюджет | Слайдер | Device Identifier (модель → ценовой сегмент) + (опц.) тариф → автокалибровка дефолта |
| Возраст/пол | Поле «возраст» | KYC Age/Match: подтверждённые → юридически чистые 18+ категории |
| Доверие участника | Нет | Tenure + SIM Swap + Device Swap → trust-вес: группы быстрее закрываются, если участники «тяжёлые» |
| Прогноз сбора | Эвристика fill×time | + Population Density + история групп региона |
| Холодный старт | Пустая лента до выбора интересов | Сегмент оператора (с согласия) → первая лента сразу осмысленная |

**Принцип:** eSIM-сигналы не добавляют новый алгоритм — они **повышают качество входных
фич уже существующего объяснимого скоринга**. Чипы «почему вам это показали» остаются,
просто причины становятся подтверждёнными.

## 5. Анти-фрод — почему это главная связка с группбаем

Атака на групповые покупки: 1 человек создаёт N аккаунтов → «собирает» группу →
получает оптовую цену на розничный объём → юнит-экономика умирает.
(Pinduoduo тратит сотни миллионов долларов в год на борьбу именно с этим.)

eSIM-ответ, по уровням:
1. **Number Verification** при входе: аккаунт = реальный номер, подтверждённый сетью (не виртуальный номер за $0.1).
2. **EID-привязка** (через оператора): N номеров на одном физическом устройстве видны.
3. **Tenure/Swap-скоринг**: свежие симки получают пониженный вес в прогрессе группы.
4. Экономика взлома: цена фейкового участника растёт с $0.1 (виртуальный номер) до цены физического устройства с контрактным номером.

Формула для питча: **«eSIM делает „1 участник группы = 1 реальный человек“ — без этого
групповые цены съедают боты, с этим опт честный»**.

## 6. Казахстанский контекст

- Операторы: Beeline (лидер), Kcell, Tele2/Altel — 99%+ рынка.
- **Коммерческих CAMARA-запусков в КЗ пока нет** (140 запусков в 50 странах — КЗ не среди них).
  НО: VEON (материнская компания Beeline KZ) — среди операторских групп, подписавших
  GSMA Open Gateway → технический путь к запуску существует, нужен бизнес-кейс. **Birge — и есть
  такой бизнес-кейс**: оператору это новый revenue stream (identity-as-a-service + комиссия
  с Carrier Billing) и удержание абонентов. Это разворачивает вопрос жюри «есть ли у вас
  договорённость с оператором?» в «мы — причина оператору запустить Open Gateway в КЗ».
- Правовая база: Закон РК «О персональных данных» — каждый сигнал §3.2 требует явного
  согласия subscriber'а; согласие собирается в приложении per-signal (не одной галочкой).

| Фаза | Что | Что нужно |
|---|---|---|
| **0. Хакатон (сейчас)** | UI-концепт: silent-auth онбординг, EID-карточка профиля, eSIM-бейдж у участников. Все данные mock | Ничего — по ТЗ физическая реализация не требуется |

| **3. Экосистема** | Carrier Billing (холд со счёта телефона), trust-скоринг групп, белый-лейбл для оператора | Полноценное партнёрство — уровень 2 из ТЗ хакатона |

## 8. Принципы приватности (зашиты в продукт)

1. **Данные не покидают оператора** — мы получаем ответы «да/нет» и категории, не сырые данные.
2. **Согласие per-signal** — каждый источник включается отдельным переключателем в профиле.
3. **Минимизация** — для рекомендаций достаточно категорий («сегмент 25–34», «Алматы»), не точных значений.
4. **Прозрачность** — чип «почему вам это показали» показывает и eSIM-сигналы: «подтверждённый регион: Алматы».

## 9. Q&A жюри (короткие ответы)

**— Что настоящего в вашей eSIM-верификации сейчас?**
Сейчас — UI-концепт по ТЗ. Прод-путь — GSMA Open Gateway Number Verification: это работающий
стандарт, 140 коммерческих запусков на 85 сетях. Доступен и через агрегаторов (Vonage, Infobip).

**— Почему eSIM, а не SMS-код?**
SMS OTP перехватывается и покупается ($0.1 за виртуальный номер). Number Verification
подтверждает владение номером на сетевом уровне, без кода вообще; eSIM-профиль
криптографически привязан к устройству (GSMA RSP-сертификаты).

**— Как вы возьмёте данные с SIM-карты? iOS же не даёт.**
Никак — и не пытаемся. Данные идут server-side от оператора по API, приложение получает
только результат. Поэтому проект и строится как партнёрство с оператором.

**— Это законно?**
Каждый сигнал — по явному согласию (ЗоПД РК), данные агрегированы до категорий,
сырые данные не покидают оператора. Fraud-сигналы (SIM Swap) — legitimate interest, стандартная мировая практика банков.

**— А если оператор не даст API?**
Фаза 1 идёт через глобальных агрегаторов CAMARA-API без прямого договора с локальным
оператором. Прямое партнёрство — это апсайд (Carrier Billing, insights), не блокер.
